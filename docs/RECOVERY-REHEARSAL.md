# Fixture-only recovery rehearsal

This is a local acceptance test, **not a production backup tool or a production recovery procedure**. It accepts no external archive or upload-directory input. It creates all source data itself and never reads a production database, password file, credential volume, or live upload directory.

## Run

Install the repository dependencies and generate Prisma Client as described in [TESTING.md](TESTING.md). PostgreSQL **17** client/server tools must be installed through an official distribution: `initdb`, `pg_ctl`, `createdb`, `pg_dump`, and `pg_restore`. Run as a non-root user:

```sh
npm run test:restore
# If automatic PostgreSQL discovery needs help:
PG_BIN=/usr/lib/postgresql/17/bin npm run test:restore
```

The command uses the existing disposable, loopback-only PostgreSQL harness. Inside that cluster, it creates unique `projecthub_test_recovery_source_<suffix>` and `projecthub_test_recovery_target_<suffix>` databases. The supplied control database is never a restore destination. The source is migrated from checked-in migrations; the target starts empty. This requires the disposable cluster's database-creation privileges, not a new account or credential.

Only the explicit test URL is accepted, with the passwordless `projecthub_test` role on `127.0.0.1`; there is no ambient `DATABASE_URL` fallback. PostgreSQL child processes receive explicit fixture connection settings and do not inherit libpq passwords, service files, or host/options overrides. The temporary artifact directory is mode 0700 and its dump file is mode 0600. Cleanup terminates owned commands/API processes, drops only successfully created fixture databases, and removes only its temporary artifacts. The outer harness then stops and removes its own cluster.

## Capture consistency

Fixture writes are complete before capture. No source API or concurrent writer is running while the test takes a custom-format `pg_dump` archive and copies the upload directory. It records a filename/length/SHA-256 manifest for the fictional files. After capture, it deliberately changes the original project, revokes a session, and changes an original file; these later changes must not appear in the restore.

The test restores into the empty target with `pg_restore --single-transaction --exit-on-error --no-owner --no-acl`, then supplies the matching captured files. The archive is generated by this test from trusted checked-in migrations and fixtures; it never restores an externally supplied dump. PostgreSQL restores execute source-defined SQL, so accepting an arbitrary archive would be a materially different operation.

This proves a **quiescent database/filesystem pair only**. PostgreSQL's consistent database snapshot does not make a separately copied upload directory atomic. A real backup needs a separately reviewed writer-drain or coordinated snapshot strategy covering all writers and both stores. Copying a live PostgreSQL data directory is not what this test does. See the official [pg_dump](https://www.postgresql.org/docs/17/app-pgdump.html) and [pg_restore](https://www.postgresql.org/docs/17/app-pgrestore.html) documentation.

## Positive acceptance

The fixture compares restored rows from every current application model and Prisma migration history against the captured values. This covers application owner IDs and roles, password-hash fields, session hashes/expiry, project content/status/feedback/version, likes, bookmarks, daily view events, audits, upload filenames/owners/bytes/states, legacy unknown sizes, and ownerless upload records. It verifies every captured file's bytes by checksum and checks that restored upload database constraints remain enforced.

A compiled API is then started only against the restored database and file directory. HTTP assertions verify:

- Active sessions resolve to the restored owner; expired sessions remain rejected
- Private projects/images remain hidden from unauthorized readers; public images remain readable
- Foreign edits and stale expected versions are rejected; a current-version edit increments the restored version
- PENDING files remain inaccessible even when referenced by an approved project, including for owner/reviewer sessions
- PENDING reservations still consume quota; a legacy unknown-size row still blocks new uploads conservatively

The inventory CLI runs against the restored copy and must finish with `complete:true`. Tests compare rows and file manifests before and after each inventory invocation to ensure it remains read-only. Expected PENDING, unknown-size, and ownerless fixture anomalies are preserved and explicitly checked, rather than silently repaired.

## Negative acceptance and inventory limits

The test intentionally damages only its restored fixture copy:

- Removing a READY file produces a missing-file inventory finding and a manifest difference.
- Truncating a READY file produces a size-mismatch finding.
- Adding an untracked file produces an orphan/missing-record finding and a manifest difference.
- Changing file contents without changing their length produces a checksum difference. The size-only inventory deliberately reports no size mismatch: it never reads/decodes file contents and is **not an integrity checksum verifier**.

An inventory exit code of zero with `complete:true` means the scan completed, not that the data is healthy. Acceptance must inspect findings and compare them with the expected recovery state. No backfill, automatic deletion, quota release, repair, or retention policy is implemented by this rehearsal.

## Session resurrection is an explicit recovery risk

The rehearsal captures an active session, deletes it from the source after capture, then proves that the restored API accepts that old session again. Restoring older rows can undo later logouts/revocations, role changes, and password changes. The test intentionally preserves this behavior as a warning, not as a security guarantee.

Before restoring real data, operators need an explicit session/account-access policy, including whether to invalidate restored sessions and reconcile security changes made after the backup. This repository does not automatically perform that policy or authorize such mutations.

## Evidence and remaining limits

The initial local rehearsal passed all **six tests** (five acceptance groups plus their parent) on PostgreSQL 17.11 with Node 22.23.3 and Node 24.19.0. Three focused fixture-guard/manifest unit tests also passed. Temporary clusters and artifacts were removed. These are small synthetic-fixture results, not recovery-time or recovery-point objectives for a real installation. Rerun against the exact intended application/schema revision.

This command is not wired into hosted CI. Hosted runner client versions must be matched explicitly to PostgreSQL 17 before adding such a gate; a successful older `pg_dump` installation does not prove compatibility with a newer server.

Unverified: production data, live/concurrent cross-store snapshots, encrypted or off-site backups, retention, WAL/PITR, SQL-role/ACL restoration, original operating-system ownership/permissions, Docker volume restoration, Dokploy credential-volume recovery, external storage, and real disaster recovery timing. `--no-owner --no-acl` intentionally excludes PostgreSQL ownership/privilege restoration; application owner IDs are a separate tested property. No deployment or production action is performed.
